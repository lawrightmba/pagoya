## Phase 1 — Templates become versioned code

1. Export all 24 dev templates into a versioned seed file in the repo (e.g., `server/seeds/paulaMessageTemplates.ts` or a SQL seed). Templates must live in code review, never as hand-inserted DB rows.
2. Write an idempotent upsert keyed on `template_key`: `INSERT ... ON CONFLICT (template_key) DO UPDATE`. Running the seed twice must be a no-op. Do not delete rows not in the seed without an explicit flag.
3. Validation step in the seed script — fail loudly if any template:
   - Has unresolved Mustache variables when rendered against a documented sample payload (add the sample payload fixture to the repo).
   - Exceeds WhatsApp message length limits.
   - Is missing es-MX content.
4. Wire the seed into the deploy path (migration step or documented release command) so dev/prod can never silently diverge again.

## Phase 2 — Guardrails (no more silent failure)

1. Startup health check: on boot, if active template count < expected constant (24), log an ERROR (not warn) with the delta and surface it to the admin dashboard. Do not crash the app.
2. Queue processor: on missing template, mark the queue item FAILED with the template_key in the error message, and log loudly. No `.catch()` swallowing — same standard as the audit-log fix.
3. Add or extend an admin endpoint: template count, active/inactive breakdown, last seed run timestamp. Read-only.

## Phase 3 — Backlog safety (CRITICAL: no message flood)

1. Before templates go live in prod, expire the stale backlog: mark all paula_send_queue items older than 7 days (or in a pre-fix failure state) as EXPIRED/DEAD. Users must NOT receive a burst of weeks-old nudges the moment this deploys.
2. Add/confirm send throttles: max 1 nudge per user per 24h, and a global per-processor-run cap (suggest 50) as a circuit breaker for the first week.

## Phase 4 — Deploy and verify

1. Staging: run seed → verify 24 rows → enqueue one canary nudge to the test WhatsApp number → confirm full pipeline (enqueue → processor → Twilio → delivered status written back).
2. Production: run seed → verify 24 rows → run Phase 3 backlog expiry FIRST → enable processor → one canary send → monitor logs and Twilio delivery for 24h before considering closed.
