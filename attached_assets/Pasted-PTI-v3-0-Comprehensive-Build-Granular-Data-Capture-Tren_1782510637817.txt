SECTION 2 — PAYMENT QUALITY SCORE (computed at insert)
═══════════════════════════════════════════════════════════

In the bill payment insert handler, after a successful payment
is confirmed, compute and store payment_quality_score (0–10)
and bill_priority_tier using these exact rules:

PAYMENT QUALITY SCORE RUBRIC (0-10):
  +3  days_before_due >= 3 (paid 3+ days early)
  +2  days_before_due >= 0 AND days_before_due < 3 (on time)
  +0  days_before_due < 0 (late — negative days_before_due)
  +2  payment_initiation = 'self' (no nudge required)
  +1  payment_initiation IN ('paula_nudge','push_notif','sms')
  +2  payment_completeness = 'full' (amount_paid >= bill_amount * 0.95)
  +1  payment_completeness = 'overpay'
  +0  payment_completeness = 'partial'
  +1  payment_channel = 'spei' (bancarization signal)
  +0  payment_channel IN ('oxxo','wallet_credit')
  Cap total at 10.

BILL PRIORITY TIER RULES:
  'essential'     — biller category IN (CFE, agua, gas, predial)
  'connectivity'  — biller category IN (Telmex, Izzi, Telcel, 
                    internet, telefonia)
  'discretionary' — everything else

If bill_amount is not available from the biller API response,
set payment_completeness = 'full' as the safe default.

If payment_initiation is not passed by the calling route,
default to 'self'.

--- 3A. P0 Signal: Income Regularity ---

From wallet_transactions (loads only, last 90 days):

avg_monthly_load_amount:
  SUM(load amounts) / 3  (3 months)

load_amount_stddev:
  STDDEV of individual load amounts over 90 days
  If fewer than 3 loads: set to NULL

income_regularity_score (0-10):
  stddev_to_avg_ratio = load_amount_stddev / avg_monthly_load_amount
  ratio < 0.15  → score 10  (very stable)
  ratio < 0.30  → score 8
  ratio < 0.50  → score 6
  ratio < 0.75  → score 4
  ratio >= 0.75 → score 2
  NULL loads    → score 0

--- 3B. P0 Signal: Obligation Ratio ---

monthly_bill_obligations:
  SUM of bill_payments.amount_paid WHERE created_at >= NOW()-90d
  divided by 3

wallet_load_to_bill_ratio:
  avg_monthly_load_amount / monthly_bill_obligations
  If monthly_bill_obligations = 0: set to NULL

--- 3C. P0 Signal: Essential Bill Ratio ---

essential_bill_ratio:
  COUNT(payments WHERE bill_priority_tier = 'essential') /
  COUNT(all payments) over lifetime
  Result as decimal 0.00–1.00
  If no payments: set to NULL

--- 3D. P1 Signal: Payday Window Consistency ---

From wallet_transactions (loads only, last 90 days),
extract DAY OF MONTH for each load:

dominant_payday_window:
  Count loads per window:
    early = day 1-7
    mid   = day 8-15
    late  = day 16-23
    end   = day 24-31
  Assign window with highest count.
  Tie: prefer earliest window.

payday_consistency:
  % of loads where day_of_month is within 3 days of the
  center of dominant_payday_window:
    early center = 4
    mid center   = 12
    late center  = 20
    end center   = 28
  Result as decimal 0.00–1.00

--- 3E. P1 Signal: Platform Tenure Derived Fields ---

platform_tenure_days:
  DATE_PART('day', NOW() - registered_at)

active_months:
  COUNT(DISTINCT DATE_TRUNC('month', created_at))
  FROM bill_payments WHERE user_id = ?

longest_gap_days:
  Find the maximum gap in days between consecutive 
  bill_payments.created_at dates for this user.
  If fewer than 2 payments: set to NULL.

--- 3F. Trend Layer: pti_trend_snapshots insert ---

After computing the current PTI score for each user,
query pti_trend_snapshots for this user's history:

  prior_30d = row WHERE computed_at <= NOW()-29d 
              ORDER BY computed_at DESC LIMIT 1
  prior_60d = row WHERE computed_at <= NOW()-59d 
              ORDER BY computed_at DESC LIMIT 1
  prior_90d = row WHERE computed_at <= NOW()-89d 
              ORDER BY computed_at DESC LIMIT 1

Compute:
  trend_30d = current_pti_total - prior_30d.pti_total 
              (NULL if no prior_30d row)
  trend_60d = current_pti_total - prior_60d.pti_total
  trend_90d = current_pti_total - prior_90d.pti_total

  trajectory:
    IF fewer than 30 days since registered_at → 'new'
    ELSE IF trend_30d > 5  → 'rising'
    ELSE IF trend_30d < -5 → 'declining'
    ELSE                   → 'stable'
    IF trend_30d IS NULL   → 'new'

  velocity:
    trend_30d / 4.3  (points per week)
    NULL if trend_30d IS NULL

--- 3G. Score Format: B2B Translation ---

pti_b2b_score:
  ROUND(350 + (pti_total / 100.0) * 500)
  Floor: 350 (even if pti_total = 0)
  Ceiling: 850 (even if pti_total > 100)
