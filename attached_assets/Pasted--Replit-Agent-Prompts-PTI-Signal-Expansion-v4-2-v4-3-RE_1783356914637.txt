# Replit Agent Prompts — PTI Signal Expansion (v4.2 → v4.3) — REV 7
### Corrects REV 6's incomplete status vocabulary. This is the last discovery item. No code changed yet.

**Changes from REV 6:**
1. **Real bug fixed — REV 6's `status='confirmed'` filter would have dropped signup bonuses.** `wallet_transactions.type` is plain `text()` with no central enum, populated across 13 write sites. Full vocabulary: 9 types (`load_oxxo`, `load_card`, `spei_in`, `load_banco`, `admin_credit`, `SIGNUP_BONUS` — uppercase, non-standard — `transfer_receive` as credits; `bill_pay`, `transfer_send` as debits) and 4 statuses (`pending`, `confirmed`, `failed`, `completed`). `signupBonusService.ts` writes the $150 signup bonus with `status='completed'`, not `'confirmed'`. REV 6's filter would have excluded real bonus money from balance reconstruction for essentially every user, understating `minBalanceBuffer30d` and falsely inflating `daysAtZeroPerMonth` — the same silent-plausible-wrong-numbers failure Stage 1.5 exists to prevent, reintroduced by its own fix.
2. **Filter corrected to a status classification, not a literal match:** balance-real = `{confirmed, completed}`, not-balance-real = `{pending, failed}`, implemented as an explicit per-status classification that throws on any unrecognized status — mirroring the type-classification guard, so a future status literal can't silently fall through either side.
3. **Ordering corrected to `COALESCE(confirmed_at, created_at)`, applied uniformly** — not `confirmed_at` alone, and not a per-type branch. `SIGNUP_BONUS`/`spei_in`/`load_banco` are written without `confirmed_at`; `bill_pay`/`transfer_send`/`transfer_receive`/`admin_credit` set it at write time. `COALESCE` handles both cases with one rule, which also resolves the debit-timestamp asymmetry REV 6 had left as an open per-type question — that hedge is removed.
4. **RESOLVED — spei_in/load_banco lifecycle confirmed by code trace, no escalation needed.** Both types are inserted `pending` and immediately transitioned to `confirmed` (with `confirmed_at` set) by `creditWallet()` (`wallet/services/wallet.ts:44`), called in the same request handler right after insert — `spei_in` via `stpWebhook.ts:217`, `load_banco` via `belvo-connect.ts`. SPEI/bank-load money is fully visible to balance features; there is no hidden funding-rail bug. The only rows with a *persistent* `pending` state are OXXO vouchers (awaiting real-world cash) and card intents (awaiting webhook) — both confirm later via the same `creditWallet` path and are correctly excluded until they do.
5. **Consequence of #4, sharpening the test plan:** because every load type gets `confirmed_at` set at the moment it becomes balance-real, `SIGNUP_BONUS` (written `status='completed'` directly, no `creditWallet` call, `confirmed_at` stays null) is the ONLY type in the balance-real row set with a null `confirmed_at`. It is therefore not just one edge case among several — it is the sole row type that exercises the `COALESCE(confirmed_at, created_at)` fallback at all. Its dedicated unit test is the single piece of evidence that the fallback ordering logic works, not just that the filter includes the right rows.

**Execution order: 0 → 0.5 → 1 → 1.5 → 2 → 3 → 4. Discovery is fully closed — no open placeholders, no pending pre-flights. REV 7 is handoff-ready as written below.**
