## Deliverable 1 — `paula_messages` Table

```sql
CREATE TABLE paula_messages (
  id            SERIAL PRIMARY KEY,
  trigger_type  VARCHAR(60) NOT NULL UNIQUE,  -- matches paula_trigger_log.trigger_type
  template_es   TEXT NOT NULL,                -- Mustache-style {{variable}} tokens
  template_en   TEXT,                         -- optional English variant, nullable for now
  active        BOOLEAN NOT NULL DEFAULT TRUE,
  cooldown_days INTEGER NOT NULL DEFAULT 7,   -- per-trigger override of global 7-day default
  updated_at    TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_paula_messages_active ON paula_messages (trigger_type, active);
```

### `cooldown_days` column

Each trigger row owns its cooldown. The trigger service reads this value at batch
start alongside the template — no hardcoded 7-day constant in application code.
Examples: `first_payment` → `cooldown_days = 9999` (effectively one-time, never
re-fires); `stalled_14d` → `cooldown_days = 7`; `pti_drop_7d` → `cooldown_days = 7`.
One-time triggers are not a separate code path — they're just rows with a very
large cooldown value.

### Template syntax — Mustache `{{variable}}`

All tokens use double-brace Mustache style: `{{nombre}}`, `{{pti_score}}`, etc.
This avoids collision with TypeScript template literals and is unambiguous in SQL
string values. The injection regex targets `{{(\w+)}}` only.

## Deliverable 2 — Variable Injection System

### Variables supported (Sprint 3)

| Token | Source |
|---|---|
| `{{nombre}}` | `users.nombre` (first name only) |
| `{{pti_score}}` | Current PTI score at trigger time |
| `{{pti_delta}}` | 30-day delta from `pti_trend_30d` view |
| `{{pti_trend}}` | Trend label: IMPROVING / DECLINING / etc. |
| `{{days_streak}}` | Days since first payment or consecutive active days |
| `{{weakest_dimension}}` | Lowest PTI dimension, mapped to Buró language |
| `{{strongest_dimension}}` | Highest PTI dimension, mapped to Buró language |
| `{{bill_category_count}}` | Distinct bill categories paid by user |
| `{{tier}}` | BRONCE / PLATA / ORO |

### Injection function (`messageEngine.ts`)

```typescript
interface UserContext {
  nombre: string;
  pti_score: number;
  pti_delta: number;
  pti_trend: string;
  days_streak: number;
  weakest_dimension: string;
  strongest_dimension: string;
  bill_category_count: number;
  tier: string;
}

export function injectVariables(template: string, ctx: UserContext): string {
  return template.replace(/\{\{(\w+)\}\}/g, (match, key) => {
    const value = ctx[key as keyof UserContext];
    if (value === undefined) {
      console.warn(`[Paula] Unresolved template variable: ${match}`);
      return match; // leave token in place, never silently drop
    }
    return String(value);
  });
}
```

**Unresolved token behavior:** log a warning, leave the raw `{{token}}` in the
message rather than sending a blank. Surfaces template bugs in the log without
garbling the user-facing message unrecoverably.

### Template cache (`loadMessageTemplates`)

Templates are fetched once at batch start — a single `SELECT * FROM paula_messages
WHERE active = true` — and held in a `Map<string, { template_es: string,
cooldown_days: number }>` for the duration of the cron run. No per-user DB call
for message content. The cache is local to the batch invocation; it refreshes
automatically on the next cron cycle.

```typescript
type TemplateCache = Map<string, { template_es: string; cooldown_days: number }>;

export async function loadMessageTemplates(): Promise<TemplateCache> {
  const rows = await db.select().from(paulaMessages).where(eq(paulaMessages.active, true));
  return new Map(rows.map(r => [r.trigger_type, {
    template_es: r.template_es,
    cooldown_days: r.cooldown_days,
  }]));
}
```

## Deliverable 3 — Trigger Service Migration

### What changes in `paulaTriggers.ts`

**Before (Sprint 2):**
```typescript
// Hardcoded string inline
const message = `${user.nombre}, hiciste tu primer pago...`;
await sendWhatsApp(telefono, message);
```

**After (Sprint 3):**
```typescript
// Load all templates once at batch start
const templates = await loadMessageTemplates();

// Per user, per trigger:
const tmpl = templates.get(triggerType);
if (!tmpl) throw new Error(`No template for trigger: ${triggerType}`);

// Dead-letter check uses cooldown_days from DB row — not hardcoded 7
const recentFire = await getLastFire(telefono, triggerType);
if (recentFire && daysSince(recentFire) < tmpl.cooldown_days) continue;

// Build context once per user (reused across all triggers for that user)
const ctx = await buildUserContext(telefono);

// Inject variables
const message = injectVariables(tmpl.template_es, ctx);

// Enqueue — do not send directly
await enqueueWhatsApp(telefono, message, triggerType, triggerId);
```

**Key constraint:** `paulaTriggers.ts` must contain zero hardcoded message strings
after this migration. The acceptance test for this is a grep:
```bash
grep -n "Hola\|llevas\|cruzaste\|nivel Oro\|Tres meses" paulaTriggers.ts
# Must return zero results
```

## Deliverable 4 — Twilio Send Queue

### Problem with fire-and-forget

Current pattern: trigger fires → Twilio called inline → success/failure not durably recorded.
If Twilio times out, message is lost with no retry. If the cron restarts mid-batch,
no way to know which sends completed.

### Solution: `paula_send_queue` table + queue processor

```sql
CREATE TABLE paula_send_queue (
  id              SERIAL PRIMARY KEY,
  telefono        VARCHAR(20) NOT NULL,
  message         TEXT NOT NULL,
  trigger_type    VARCHAR(60),
  trigger_log_id  INTEGER REFERENCES paula_trigger_log(id),
  status          VARCHAR(20) NOT NULL DEFAULT 'PENDING',
    -- PENDING | SENDING | SENT | FAILED | DEAD
  attempts        INTEGER NOT NULL DEFAULT 0,
  last_attempt_at TIMESTAMPTZ,
  sent_at         TIMESTAMPTZ,
  error_detail    TEXT,
  created_at      TIMESTAMPTZ DEFAULT NOW(),

  CONSTRAINT valid_status CHECK (
    status IN ('PENDING', 'SENDING', 'SENT', 'FAILED', 'DEAD')
  )
);

CREATE INDEX idx_send_queue_pending ON paula_send_queue (status, created_at)
  WHERE status IN ('PENDING', 'FAILED');
```

### Queue processor

Runs every 2 minutes (separate from the 6-hour trigger cron).

```
LOOP:
  SELECT up to 10 rows WHERE status IN ('PENDING', 'FAILED') AND attempts < 3
    ORDER BY created_at ASC
    FOR UPDATE SKIP LOCKED          ← safe for future multi-process

  FOR EACH row:
    SET status = 'SENDING', attempts++, last_attempt_at = NOW()
    CALL Twilio sendMessage()
    IF success:
      SET status = 'SENT', sent_at = NOW()
      UPDATE paula_trigger_log SET whatsapp_sent = true WHERE id = trigger_log_id
    IF failure:
      SET status = 'FAILED', error_detail = error.message
      IF attempts >= 3:
        SET status = 'DEAD'   ← never retried again, visible for manual review
```

### Retry policy

| Attempts | Status | Action |
|---|---|---|
| 1 | FAILED | Retry on next processor run (~2 min) |
| 2 | FAILED | Retry on next processor run (~2 min) |
| 3 | DEAD | No further retries — surfaced in admin |

DEAD messages are never deleted. They're the audit trail for delivery failures.
