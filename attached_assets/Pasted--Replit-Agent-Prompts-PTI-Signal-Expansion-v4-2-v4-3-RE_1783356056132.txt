# Replit Agent Prompts — PTI Signal Expansion (v4.2 → v4.3) — REV 6
### Final hardening pass. Fixes a real balance-corruption bug in Prompt 1.5 and two days_from_due notes. No code changed yet.

**Changes from REV 5:**
1. **Real bug fixed — Prompt 1.5 now filters `wallet_transactions` by status and orders by `confirmed_at`, not `created_at`.** `wallet_transactions.status` (notNull, default `'pending'`) has vocabulary `pending` / `confirmed` / `failed`. Only `confirmed` rows are real balance. Without this filter, `reconstructBalanceSeries` would have counted pending OXXO vouchers and failed card loads as spendable money — the exact same class of error as the `bill_payments` `fallido` issue, but silently corrupting every Stage 2 cash-flow feature (`minBalanceBuffer30d`, `daysAtZeroPerMonth`, `drawdownVelocity`, load features) rather than just the timing ones. Additionally, credits must be ordered by `confirmed_at` (tz-aware) — a load created `pending` on the 1st and confirmed on the 5th only becomes spendable on the 5th; ordering by `created_at` would credit it four days early and skew both the 30-day buffer minimum and `drawdownVelocity`'s 72-hour attribution window.
2. `days_from_due` sign convention upgraded from "working assumption" to **confirmed by code**: schema comment states positive = early, negative = late, and the populating formula (`payment_day − EXTRACT(DAY FROM NOW())`) mathematically produces exactly that. No re-check caveat needed.
3. **New known limitation documented, not yet fixed:** that same formula has no month-rollover handling — a bill due the 2nd, paid the 28th, computes as −26 (reads as wildly late) rather than the true few-day lateness, and the reverse near the other boundary. This inflates `paymentTimingVarianceDays`, the designated primary timing signal, with boundary artifacts rather than real behavioral variance. Documented as a docstring caveat in Prompt 1; fixing the underlying formula is out of scope for this round (it lives in existing v4.2 code, not new code) but flagged for a future pass since it affects a feature this plan is built around.
4. Prompt 2 Part A's hedge ("confirm no analogous states exist... before assuming otherwise") is removed — the analogous state was found, and the fix lives once in the Stage 1.5 helper. Part A now simply states the filtering is handled upstream and must not be re-applied downstream.

**Execution order: 0 → 0.5 → 1 → 1.5 → 2 → 3 → 4. All discovery items are now closed.**

## PROMPT 1.5 — Balance reconstruction helper (REV 6 — status filter + confirmed_at ordering, the substantive fix)

```
CONTEXT: wallet_transactions has no balance-after column and no signed-amount column (amount_mxn is unsigned). Credit/debit must be inferred from `type`. Production data currently contains only load_oxxo and load_card (3 rows total) — the full type vocabulary cannot be enumerated from data and must come from the application's type definitions in code.

STATUS GROUND TRUTH (confirmed by code read): wallet_transactions.status is notNull, default 'pending', with a dedicated wallet_tx_status_idx. Confirmed vocabulary: pending (voucher issued/card intent created, no money in wallet yet), confirmed (cash deposited/card charged, confirmed_at is set — this is the ONLY balance-real state), failed (abandoned/declined load). This is the same class of problem as bill_payments' fallido rows, and it lives in this helper because every Stage 2 feature depends on it.

PRE-FLIGHT:
1. Find the authoritative source of wallet_transactions.type values in code (enum/type union) — do not rely on the 2 distinct values seen in production.
2. Confirm the status column's exact vocabulary and the confirmed_at column's nullability (should be null unless status='confirmed') by reading the write paths.
3. Confirm bill_payments.created_at is naive and wallet_transactions.created_at/confirmed_at are tz-aware.

TASK — new module walletBalanceReconstruction.ts:
1. Explicit, exhaustive credit/debit classification for EVERY type value found in the code-level enum (not just the two observed in prod). Throw on any truly unrecognized value.
2. reconstructBalanceSeries(userTransactions): 
   a. FILTER to status = 'confirmed' before doing anything else. Pending and failed rows are excluded entirely — they are not balance events regardless of type.
   b. ORDER confirmed rows by confirmed_at (not created_at) for credit-type transactions, since a load only becomes spendable balance at confirmation, not at initiation. If debit-type transactions (spends/transfers) don't have a separate confirmed_at distinct from created_at, use created_at for those specifically, but document this asymmetry explicitly in-code rather than assuming a uniform timestamp field across all types — confirm the actual columns available on debit-type rows before deciding.
   c. Return a running-balance series as {timestamp, balance} points after each confirmed transaction, using the resolved timestamp from (b).
   d. Document the opening-balance assumption as a named constant.
3. toComparableTimestamp(): normalizes bill_payments.created_at (naive) to the same tz assumption as wallet_transactions, for every future cross-table comparison.
4. Unit tests, covering ALL of the following (not a subset):
   - single transaction
   - same-timestamp transactions (order ambiguity)
   - a full month of interleaved loads/spends (synthetic)
   - an unrecognized type (must throw)
   - zero transactions (empty series, not error)
   - a pending-then-confirmed load: balance must rise at confirmed_at, NOT at created_at, and must not appear in the series at all while still pending
   - a failed load: must never affect the balance series at any point, at any timestamp
   - a mix of confirmed and non-confirmed rows for the same user in the same window, verifying only confirmed rows are counted
5. Do NOT wire into PTIDataSnapshot yet.

GUARDRAILS: no dependency on pti.ts. Pure functions, fully unit tested, no live DB writes.

DEFINITION OF DONE: reconstructBalanceSeries() filters to status='confirmed' and orders by confirmed_at for credits (with the debit-timestamp question explicitly resolved and documented, not assumed); toComparableTimestamp() exists; all eight unit-test cases above pass, including the pending/failed exclusion tests; unrecognized types throw.
```
