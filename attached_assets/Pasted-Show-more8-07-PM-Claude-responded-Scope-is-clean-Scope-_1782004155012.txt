Item 3 — modules_unlocked: derived vs. stored JSONB
Same dual-write question as financial_literacy_score. The trigger log already has everything needed:
sqlSELECT trigger_type FROM paula_trigger_log
WHERE telefono = $1
AND trigger_type LIKE 'module_unlock_%'
ORDER BY fired_at ASC
That returns ['module_unlock_2', 'module_unlock_3'] — which maps trivially to human-readable labels for prompt injection without a separate JSONB column to maintain. Same pattern as item 1, same rationale: paula_trigger_log is already the append-only canonical record, cooldown_days = 9999 guarantees each fires exactly once.
Recommendation: derive it in buildUserContext alongside financial_literacy_score, return it as modules_unlocked: string[] in UserContext, serialize to a readable string for prompt injection. Zero schema changes.
The only reason to store JSONB on users would be if you needed to query "all users who have completed module 3" at batch scale without hitting the trigger log. That's a Sprint 6 concern (readiness gate checks literacy_score >= 3), and even there the COUNT query is fast on an indexed table. Not worth the dual-write risk now.
